## Contexte
Spec 07, `03-fin-contrat-gel.md` et décision D3 : le client demande la fin, la console la traite ; export complet remis (manifeste d'empreintes) ; accusé de l'administrateur du client (qui, quand, empreinte du manifeste reçu) ; effacement à J+30 après l'accusé, rappel à J+23, JAMAIS pendant un gel, jamais avant la remise ni avant l'accusé ; sans accusé : relances à J+7, J+14, J+30 après la remise, puis le cas passe à une personne d'Axion (Q4 : aucun effacement automatique sans accusé). Les durées (30, 23, 7, 14) sont des réglages de la console et de la décision D3, passés en ARGUMENT. Cas T-ABO-14 (accusé le 1er mars, aucun gel : effacement demandé le 31 mars, pas avant), T-ABO-15 (gel posé le 20 mars, levé le 10 avril : effacement demandé le jour de la levée), T-ABO-16 (aucun accusé 60 jours après la remise : 0 effacement, 3 relances, cas transmis).

## À faire
1. `packages/noyau/src/abonnement/fin-contrat.ts` (types `FinContrat` et `Gel` de L07-T00) :
   - `type ParametresFinContrat = { joursAvantEffacement: number; joursRappelAvantEffacement: number; joursRelancesSansAccuse: readonly number[] }` ; `verifierParametres(p)` : entiers >= 1, rappel strictement inférieur à l'attente, relances non vides, triées et dédoublonnées dans le résultat, sinon `parametre_invalide` ;
   - `enregistrerRemise(fin, { manifesteEmpreinte, horodatage })` → `{ fin; evenement: fin_contrat.export_remis }` (empreinte vérifiée) ;
   - `enregistrerAccuse(fin, { empreinteRecue, auteur, horodatage })` → `{ fin; evenements: [fin_contrat.accuse, fin_contrat.effacement_planifie] }` : pas de remise → `pas_de_remise` ; déjà accusé → `deja_accuse` ; empreinte différente de celle du manifeste → `empreinte_differente` ; auteur vide → `auteur_manquant` ;
   - `effacementPrevuLe(fin, p)` → `ajouterJours(date de l'accusé, joursAvantEffacement)` ou `null` sans accusé ;
   - `peutDemanderEffacement(fin, aujourdhui, p)` → `{ permis: boolean; raison: 'pas_de_remise' | 'pas_d_accuse' | 'gel_actif' | 'trop_tot' | null }` ; ordre : remise, accusé, gel (`gelModule.actif` OU `gelConsole`), date ; `permis` seulement si `aujourdhui >= effacementPrevuLe` ;
   - `rappelDu(fin, aujourdhui, p)` → vrai le jour `effacementPrevuLe − joursRappelAvantEffacement` seulement, sans gel ;
   - `relancesDues(fin, aujourdhui, p, dejaEnvoyees: readonly number[])` → `{ relances: number[]; transmettreAAxion: boolean }` : sans accusé, chaque délai de relance atteint (`aujourdhui >= remise + délai`) et pas encore envoyé ; `transmettreAAxion` vrai quand le plus grand délai est atteint et qu'il n'y a pas d'accusé ; avec accusé → `{ relances: [], transmettreAAxion: false }`.

## Pièges
Règles du noyau. Aucun nombre de jours en dur dans `src` : les noms de paramètres commencent par `jours` et la garde L01-T02 refuserait un littéral sur une ligne qui contient `delai` ou `duree` ; ne pas nommer de variable `delai30`. Les valeurs de la spec (30, 23, 7, 14) ne vivent que dans les tests. Une échéance qui tombe pendant un gel reste due à la levée : ne jamais « décaler » la date, seulement refuser tant que le gel dure. Sensible (effacement de données) : relecture Opus obligatoire.
