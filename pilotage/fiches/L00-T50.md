## Contexte
Audit console du 08/11/2026 : aucun port de session dans le code ; L04-T51, L05-T58, L13-T49, L06-T36, L08-T53 et L09-T49 supposent chacune leur session. Préfixes divergents : `/api/compta/v1/societes/{s}` (L04-T51, L05-T58, L06-T38, L15-T60), `/api/v1/societes/{sid}` (L11-T38), `/v1/societes/{sid}` (specs 09 et 10, L09-T49, L10-T52). L'ADR 0060 de la console (zone `/compta/**`, même session, revendications du jeton) n'est pas réglé (D29, question 1 de l'audit). Briques sur main : `Role` et `Permission` (`packages/noyau/src/securite/types.ts`, L06-T00), `Revendications` et `exigerNiveau` (`connexion.ts`, L06-T09 : `acr` « mfa » et connexion récente), `verifierSocieteDeLaRequete` (`societe.ts`, L06-T08). Identifiants opaques : la correspondance avec l'identité Keycloak et `cli_<id>` n'est pas connue. Plusieurs organisations (D4) après J10 : le type porte déjà une liste, un seul choix au MVP. Valeur par défaut du préfixe : `/api/compta/v1/societes/{s}` (forme la plus fréquente ; la spec 01/12 donne la partie `/v1/societes/{s}`, le montage `/api/compta` est l'hypothèse en attente de l'ADR 0060). Tout s'écrit contre une interface et un faux (décision J3a de Will). Décision de Will du 08/11/2026 : « fais tout ce qui est nécessaire selon tes recommandations ».

## À faire
1. Tests d'abord. `__tests__/suite-session.ts` exporte `suiteSession(nom, fabrique)` (fabrique : `(sessions: Readonly<Record<string, Session>>) => PortSession`) : test de contrat que l'adaptateur réel (L06-T36) devra passer.
2. `port.ts` :
   - `Session { personneId; nature: 'personne' | 'service'; organisationId; organisations: readonly string[]; societeId; societes: readonly string[]; roles: readonly Role[]; permissions: readonly Permission[]; revendications: Revendications }` (aucun nouveau rôle ni permission) ;
   - `PortSession { lire(reference: string | null): Promise<Session | null> }` (référence opaque de session) ;
   - `ErreurSession` (`code` : `session_invalide`, `organisation_refusee`) ; `verifierSession(brut: unknown): Session` : rôle ou permission inconnus, `societeId` hors `societes`, `organisationId` hors `organisations`, liste vide ou champ inconnu = `session_invalide` ; rend une copie gelée ;
   - `exigerPermission(s, p)` → `{ ok: true } | { ok: false; raison: 'permission_manquante' }` ; `exigerPersonne(s)` → `{ ok: true } | { ok: false; raison: 'compte_de_service' }` ;
   - `exigerNouvelleConnexion(s: Session | null, operation: OperationSensible | 'ordinaire', maintenantMs, reglages: ReglagesConnexion, derniereRecuperationMs?: number)` → `VerdictNiveau` : délègue à `exigerNiveau` avec `s.revendications`, en transmettant `derniereRecuperationMs` (raison `recuperation_recente`) (session nulle = `non_authentifie`) ;
   - `choisirOrganisation(s, organisationId, societesDeLOrganisation)` → nouvelle `Session` (société courante = la première de la liste) ou `organisation_refusee` si la personne n'en est pas membre ou si la liste est vide.
3. `memoire.ts` : `creerFauxSessions(sessions)` → `PortSession` ; chaque session passe par `verifierSession` à la création ; référence inconnue ou nulle → `null` ; rend une copie (la modifier ne change pas le faux).

Pas d'export par `index.ts` (fichier commun).

Dans `session.test.ts`, en plus de la suite sur le faux : `role-inconnu-refuse`, `societe-hors-liste-refusee`, `permission-manquante`, `compte-de-service-refuse`, `nouvelle-connexion-recente-acceptee`, `nouvelle-connexion-trop-ancienne-refusee`, `sans-mfa-refuse`, `organisation-non-membre-refusee`.
