## Contexte
Spec 05, fichier 08 §1 à §3 : le directeur de conformité appelle 4 chefs de pôle, consolide leurs constats, fixe les priorités, décide l'escalade vers l'utilisateur (comptable invité ou administrateur, D44), ne produit AUCUNE écriture. Un pôle propriétaire par type de constat ; constat sans propriétaire = erreur de configuration. Refus d'un chef de pôle → objet « à vérifier ». Jeu du fichier 10 : 40 bloquants sur 40 escaladés au bon pôle.

## À faire
1. `packages/noyau/src/agents/hierarchie.ts` (`POLES`, `GRAVITES_CONSTAT` de L05-T00) :
   - `verifierPropriete(typesConnus, table: Record<type, Pole>)` → liste des types sans propriétaire et des pôles inconnus ;
   - `consolider(constats: { id; type; gravite; pole?; refusParChef? }[], table)` → `{ constats triés (critique, majeur, mineur, info, puis id) ; escalades: { id; pole; vers: 'utilisateur' }[] ; a_verifier: id[] ; effets: [] }` ; tout `critique` est escaladé ; constat d'un type sans propriétaire = `ErreurChat('parametre_invalide')` ; `refusParChef` → `a_verifier` ; deux constats du même id = erreur ;
   - le résultat n'a jamais d'écriture (`effets` toujours vide, typé `readonly never[]`).
2. Tests nommés : `table-complete`, `type-sans-proprietaire-rouge`, `pole-inconnu-rouge`, `tri-par-gravite-puis-id`, `quarante-bloquants-escalades` (jeu inventé, 10 par pôle), `refus-du-chef-a-verifier`, `id-en-double-refuse`, `aucun-effet`, `liste-vide`, `ordre-d-entree-sans-effet` (liste inversée = même résultat).

## Hors périmètre
Pas de rédaction par le modèle, pas de règles REGLE-000 à 170, pas de destinataire réel (l'escalade dit « utilisateur habilité »).

## Pièges
Règles du noyau (eslint). Le destinataire d’une escalade est toujours l’utilisateur habilité, jamais un professionnel extérieur (D44).
