## Contexte
Spec 03, §07 : le rapport du FEC porte « l'empreinte SHA-256 du fichier livré » ; deux productions d'un exercice clôturé donnent la même empreinte (K3). Spec 10 et 11 : archive figée et paquet pour le comptable portent un `MANIFESTE.sha256` vérifiable (« manifeste recalculé = manifeste stocké », P4). Un seul module sert le FEC, l'archive et le paquet.

## À faire
1. `packages/noyau/src/documents/empreinte.ts` (import `createHash` de `node:crypto`, aucune dépendance ajoutée) :
   - classe locale `ErreurDocument extends Error` avec `code` : `nom_invalide`, `nom_en_double`, `manifeste_illisible` ;
   - `empreinteSha256(octets: Uint8Array | string)` → 64 caractères hexadécimaux minuscules (une chaîne est encodée en UTF-8) ;
   - `manifeste(fichiers: { nom: string; octets: Uint8Array | string }[])` → texte : une ligne « empreinte, deux espaces, nom » par fichier, triée par nom (ordre de chaîne), lignes séparées par un saut de ligne LF, texte terminé par LF ; nom vide, ou contenant une barre oblique, une barre oblique inverse, un LF ou un CR = `nom_invalide` ; deux fois le même nom = `nom_en_double` ;
   - `lireManifeste(texte)` → `{ nom, sha256 }[]` ; ligne mal formée = `manifeste_illisible` ;
   - `verifierManifeste(texte, fichiers)` → `{ ok: boolean; manquants: string[]; modifies: string[]; enTrop: string[] }`.
2. Tests nommés : `vecteur-connu-abc` (SHA-256 de `abc` = `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`), `chaine-et-octets-identiques`, `manifeste-trie-par-nom` (entrée dans l'ordre inverse : même texte), `manifeste-recalcule-identique`, `fichier-modifie-detecte` (un octet changé), `nom-en-double-refuse`, `nom-avec-barre-refuse`.

## Hors périmètre
Pas de scellement ni d'horodatage qualifié (table `scellement` vide, FEC-019). Pas d'écriture sur disque.
