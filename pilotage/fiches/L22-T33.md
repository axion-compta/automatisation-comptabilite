## Contexte
Les valeurs normatives vivent dans une table unique (`packages/parametres`, L01-T14) et `garde:litteraux` (L01-T02) refuse les littéraux dans le code. Rien ne vérifie que les spécifications (hors de ce dépôt) n'écrivent pas une valeur contraire à la table, ni une valeur fausse déjà connue (par exemple une règle de réserve légale ou un compte réservé à une autre forme de société).

## À faire
1. Tests d'abord, spécifications FICTIVES écrites dans un dossier temporaire.
2. `valeurs-interdites.json` : liste `{ id, motif, motifRegex, formes }` (forme de société concernée) ; chaque entrée décrit une erreur connue en termes techniques, sans recopier de texte de spécification.
3. `specs-alignees.mjs` : `analyser(dossier, interdites)` → liste `{ fichier, ligne, id }` ; lance sur `SPECS_DOSSIER` si la variable existe ; code de sortie 1 si au moins une valeur interdite est trouvée ; n'affiche que fichier, ligne et identifiant (aucun extrait).
4. Tests nommés : `spec-fictive-saine-aucun-ecart`, `valeur-interdite-trouvee-ligne-exacte`, `forme-non-concernee-ignoree`, `sortie-sans-extrait`, `sans-variable-ignore-avec-message`, `json-bien-forme`.

## Hors périmètre
Correction des spécifications elles-mêmes (dépôt privé), nouvelle garde, CI.

## Pièges
Aucun chemin du dépôt privé écrit dans le dépôt public. `garde:litteraux` doit rester vert : le JSON est une donnée de test d'alignement, pas une valeur légale utilisée par le code.
