## Contexte
Spec 06, fichier 03, règle 5 : la matrice des droits est une donnée (`MATRICE_PROPOSEE`, `packages/noyau/src/securite/matrice.ts`, L06-T04), ce qui permet en V2 des rôles composés case par case. Critère du registre : un rôle créé n'excède jamais les droits de son créateur. Décision d'une action : `autoriser` et `capacites` (`autoriser.ts`, `capacites.ts`).

## À faire
1. Tests d'abord.
2. `roles-personnalises.ts` :
   - type `RolePersonnalise = { id; nom; cases: Readonly<Partial<Record<Action, 'O' | 'N' | 'sep'>>>; creePar: string }` ;
   - `creerRolePersonnalise(createur: ContexteAutorisation, demande)` : refuse (`ErreurSecurite`) toute case `O` ou `sep` sur une action que `capacites(createur)` ne permet pas ; refuse un nom vide ou blanc, une action inconnue, une case hors liste ; une case absente vaut `N` ;
   - `caseRolePersonnalise(role, action)` : lecture pure, `N` par défaut ;
   - un rôle personnalisé ne peut jamais porter une action d'écriture (`ACTIONS_ECRITURE`) pour une identité `personnel_axion` (PLA-140), même si la demande le prévoit.
3. Tests nommés : `role-dans-les-droits-du-createur-accepte`, `case-au-dela-du-createur-refusee`, `separation-des-taches-conservee` (créateur en `sep` : le rôle ne peut pas recevoir `O`), `case-absente-vaut-non`, `nom-vide-refuse`, `action-inconnue-refusee`, `personnel-axion-jamais-en-ecriture`.

## Hors périmètre
Table `a_compta.regle_permission` (L06-T39), route de création et écran de l'équipe : fiches à écrire après la V0. Modification de `matrice.ts`, `types.ts` ou `autoriser.ts`.

## Pièges
Fiche sensible (droits) : relecture Opus, fusion par Will seul. Aucune escalade possible par composition de deux rôles : le contrôle se fait toujours contre les capacités du créateur au moment de la création.
