## Contexte
`garde:appels` : seul `apps/web/src/api.ts` appelle le réseau. Pour que chaque écran lise sa route sans toucher `api.ts`, il faut une fonction générique de lecture, validée par les schémas zod du contrat.

## À faire
1. `api.ts` : ajouter `lire<T>(chemin, schema, signal?)` : `GET` vers `new URL(chemin, location.origin)` ; réponse 2xx validée par `schema` ; sinon lève `ErreurLecture { statut, code }` avec `code` parmi `acces_refuse` (403), `introuvable` (404), `conflit` (409), `verrouille` (423), `serveur` (5xx), `reseau` (pas de réponse), `reponse_invalide` (schéma). Ne rien changer aux fonctions existantes.
2. `donnees/lecture.tsx` : `FournisseurDonnees` (un `QueryClient` de `@tanstack/react-query`, sans nouvelle tentative sur une erreur 4xx) et `useLecture(chemin, schema)` → `{ etat: 'chargement' | 'erreur' | 'vide' | 'pret', donnees?, erreur? }` ; `vide` si l'enveloppe a `total === 0`.
3. Tests nommés : `lire-ok-valide-par-schema`, `lire-403-acces-refuse`, `lire-423-verrouille`, `lire-reseau`, `lire-reponse-invalide`, `use-lecture-etats-successifs`, `use-lecture-vide`.

## Hors périmètre
Pas d'écriture (POST, PUT), pas d'écran.

## Pièges
`fetch` est remplacé dans les tests par `vi.stubGlobal` (comme `api.test.ts`). En jsdom, une URL relative passée à `fetch` échoue : d'où `location.origin`.
