## Contexte
Suite de la relecture de L01-T18. Dans `lignes.ts`, `ordonner` trie sur la date de validation telle qu'elle est reçue, avant tout contrôle de forme : une date mal formée n'est refusée qu'ensuite, et seulement si l'écriture a des lignes. Quand `numero` est absent, la colonne `ecritureNum` est vide et le tri se fait sur une chaîne vide : ce repli n'est testé nulle part.

## À faire
1. `dateValidation` : contrôler le format `AAAA-MM-JJ` (date réelle) dès la lecture, donc avant le tri, et lever `ErreurFec('date_invalide')`.
2. Tests : date de validation `2026-3-1`, `20260331`, `2026-02-30`, `2026-13-01`, chaîne vide, `NaN` en texte ; écriture sans ligne mais avec date mal formée : refus ; écriture non validée avec date mal formée : ignorée comme avant.
3. Test du repli `numero` absent : colonne `ecritureNum` vide, ordre stable entre deux écritures sans numéro de même date, un numéro présent passe avant ou après selon le tri `numeric` (valeurs inventées, attendu écrit à la main dans le test) ; ordre d'entrée inversé donne le même fichier.

## Hors périmètre
Pas de changement de `format.ts`. Pas de nouvelle colonne.

## Pièges
Aucun changement de comportement pour une date valide. Les tests de L01-T18 restent verts sans modification. Sensible : fusion par Will.
