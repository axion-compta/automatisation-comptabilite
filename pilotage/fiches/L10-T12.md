## Contexte
Spec 10, fichier 01, règles 5 et 7 : même SIREN, ou même nom normalisé + même code postal → PROPOSITION de fusion, jamais faite seule ; une fusion garde le plus ancien code auxiliaire et ne change aucune ligne validée. Un client avec un solde 411 non nul ne peut pas être désactivé. Cas limite : un particulier qui devient professionnel = nouvelle valeur datée, factures passées inchangées.

## À faire
1. `packages/noyau/src/ventes/clients-doublons.ts` :
   - `doublonsProbables(clients: { code; nom; siren?; codePostal?; creeLe }[])` → paires `{ a; b; motif: 'meme_siren' | 'meme_nom_et_code_postal' }`, chaque paire une seule fois, ordre stable ;
   - `planFusion(a, b)` → `{ codeConserve; codeRetire }` : `creeLe` le plus ancien, puis code le plus petit ;
   - `peutDesactiver(solde411: Centimes)` → vrai seulement si 0 ;
   - `natureALaDate(historique: { nature; depuis }[], date)` → nature en vigueur (dernière `depuis` ≤ date), `a_confirmer` si aucune.
2. Tests nommés : `meme-siren-sous-deux-noms` (« Immobilière Marceau » et « SCI Marceau »), `meme-nom-et-code-postal`, `meme-nom-code-postal-different-pas-doublon`, `paire-unique-ordre-stable` (entrée mélangée, même sortie), `fusion-garde-le-plus-ancien`, `solde-non-nul-pas-de-desactivation` (1 et -1 centime), `particulier-devenu-professionnel-date`, `entrees-invalides` (dates invalides ; solde NaN ou 1.5 ; liste vide → aucune paire).
