## Contexte
Spec 10, fichier 04, point 3 : un crédit qui regroupe plusieurs factures est réparti dans l'ordre choisi par la personne ; défaut proposé : la plus ancienne d'abord. Le reste éventuel est un trop-perçu, jamais un produit.

## À faire
1. `packages/noyau/src/ventes/repartition-credit.ts` :
   - `repartirCredit(credit, factures: { id; resteDu; dateFacture }[], ordre?: string[])` → `{ affectations: { factureId; montant }[]; reste: Centimes }` ;
   - ordre par défaut : `dateFacture` croissante puis `id` ; `ordre` fourni : identifiants sans doublon, tous connus (sinon `ErreurVente('ordre_invalide')`) ; factures absentes de `ordre` non servies ;
   - chaque facture reçoit `min(reste du crédit, resteDu)` ; facture à reste dû nul ignorée ; Σ affectations + reste = crédit.
2. Tests nommés : `plus-ancienne-d-abord`, `ordre-choisi`, `credit-insuffisant-derniere-partielle`, `credit-excedent-reste`, `meme-date-trie-par-id`, `ordre-inconnu-ou-double-refuse`, `montants-invalides` (crédit 0, négatif, 1.5, NaN, Infinity ; reste dû négatif), `liste-vide-tout-en-reste`.

## Hors périmètre
Écritures : l'appelant appelle L10-T05 une fois par affectation.

## Pièges
Règles du noyau (eslint) comme L01-T06 : ni littéral décimal, ni `/`, ni `Math.round`, ni `parseFloat`, ni `toFixed` ; montants en `Centimes` de `../argent/index.js`.
