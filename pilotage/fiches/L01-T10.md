## Contexte
Spec 01, §04 : `POST …/lettrages` : « lettrage total ou partiel » ; T-ECR-5 : « lettrage ajouté : empreinte de l'écriture identique avant et après » (le lettrage est un lien ajouté, jamais une modification de la ligne). Dans l'interface, le mot « lettrage » n'est pas montré au client : seulement « relier paiements et factures ». Ici, c'est le nom technique.

## À faire
1. `packages/noyau/src/ecritures/lettrage.ts` :
   - type `LigneALettrer { id: string; compte: string; auxiliaire?: string; debit: Centimes; credit: Centimes; lettre?: string }` ;
   - `lettrer(lignes, code)` → `{ code, partiel: boolean, reste: Centimes, liens: { ligneId, code }[] }` ; refus `comptes_differents` (compte ou auxiliaire différents), `deja_lettree`, `moins_de_deux_lignes`, `code_invalide` ; `partiel` vrai si Σ débits ≠ Σ crédits, `reste` = différence signée ;
   - `prochainCode(codesExistants)` : `A` … `Z`, puis `AA`, `AB` … (le plus petit code libre dans cet ordre) ;
   - le résultat ne contient que des liens : les lignes reçues ne sont jamais modifiées.
2. Tests nommés : `lettrage-total`, `lettrage-partiel-reste`, `comptes-differents-refuse`, `ligne-deja-lettree-refusee`, `prochain-code-apres-z`, `lignes-intactes`.

## Hors périmètre
Pas de rapprochement bancaire, pas de délettrage automatique.

## Pièges
Mêmes règles du noyau que L01-T06. Sensible (lettrage = argent) : fusion par Will.
