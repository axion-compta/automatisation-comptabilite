## Contexte
Spec 15, AL-R2 et AL-R4 : catalogue versionné de 11 alertes au MVP ; 22 en V1 et 8 en V2 s'ajouteront sans changer le moteur ; 100 % des alertes MVP ont une `action_principale` ; chaque alerte a son jeu de 3 cas. La table `regle_alerte` en base viendra avec la persistance (L15-T59) : ce module en est la source.

## À faire
1. `alertes/catalogue.ts` : `RegleAlerte { code: 'ALR-01'…'ALR-11'; version: number; perimetre: 'MVP' | 'V1' | 'V2'; entreeMenu: string; graviteBase; nature: NatureRegle; actionPrincipale: string; actif: boolean; evaluer }` ; `CATALOGUE_MVP` gelé, qui relie chaque code à sa fonction de L15-T15 à L15-T17 ; `entreeMenu` parmi les identifiants du menu (`activite`, `mois`, `banque`, `factures`, `declarations`, `documents`) ; `actionPrincipale` = code d'action (ex. `ouvrir_declaration_tva`), sans lien obligatoire au registre des outils du chat (hors lot).
2. Tests nommés : `onze-regles-mvp`, `codes-uniques-et-ordonnes`, `toutes-ont-une-action-principale` (non vide, forme `[a-z_]+`), `entree-menu-connue`, `nature-coherente` (ALR-08 nature `autre` ; ALR-01, 04 `echeance_legale` ; ALR-09 `argent` ; ALR-05, 06, 07 `blocage`), `trois-cas-par-regle` (lit les fichiers de tests de `regles/__tests__` et vérifie, pour chaque code, la présence des trois noms de test « se-declenche », « ne-se-declenche-pas » ou équivalent déclaré, « seuil-exact » ou équivalent déclaré dans une table du test).

## Hors périmètre
Pas de table en base, pas de migration.

## Pièges
Le test `trois-cas-par-regle` doit rougir si on supprime un test d'une règle. Ne pas modifier les fichiers de `regles/`.
