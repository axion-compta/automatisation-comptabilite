## Contexte
Débloquée par la décision de Will du 07/11/2026 (D42 hébergeur Hetzner : le script tourne sur le serveur de l'hébergeur ; J3a donné avec quatre conditions : données FICTIVES seulement, fiches sensibles relues par Opus, aucune mise en production sans le feu vert J10, ce qui exige le vrai schéma de la console s'écrit contre une interface et un faux serveur). La persistance de `connecteur_sante` et la planification réelle (BullMQ de la console) attendent la console : ici, tout passe par des interfaces.
Spec 14, `01` E : un script sans IA essaie chaque connecteur une fois par jour ; 2 échecs de suite = `degrade`, affiché au client ; retour à `ok` = bandeau retiré ; aucune donnée client dans le script. La décision pure existe (`packages/noyau/src/sources/connecteurs.ts`, L14-T07). Modèle de forme : `apps/serveur/src/taches/controles-nocturnes.ts` (L12-T51).
La route `GET /sources/etat` est la fiche L14-T32 (encore à faire) : cette fiche ne la touche pas et ne modifie aucun fichier commun (`routes.ts`, `app.ts`, `openapi.json`). Elle fournit seulement `lireEtatClient`, que L14-T32 ou une fiche suivante branchera.

## À faire
1. `apps/serveur/src/taches/sante-connecteurs.ts`, contre des interfaces :
   - `PortEssai { essayer(connecteur: string, signal: AbortSignal): Promise<boolean> }` (essai technique du connecteur, sans donnée client) ;
   - `PortSante { lire(clientId: string): Promise<readonly SanteConnecteur[]>; ecrire(clientId: string, santes: readonly SanteConnecteur[]): Promise<void> }` ;
   - `passerSanteQuotidienne({ clients, connecteurs, jour, seuils, delaiMs, essai, stock, alerter })` : pour chaque client puis chaque connecteur, un essai, `enregistrerEssai` (ou `santeInitiale` s'il n'existe pas encore), écriture ; un client après l'autre ;
   - essai qui lève une exception ou dépasse `delaiMs` = échec (`ok: false`), jamais une réussite ; l'essai est interrompu par le `AbortSignal` ;
   - relancé le même jour : `meme_jour` de L14-T07 rattrapé, état inchangé, résultat `deja_fait` (idempotent) ;
   - alerte d'exploitation `{ code: 'connecteur_degrade' | 'connecteur_en_panne', clientId, connecteur }` seulement au passage vers cet état (pas tous les jours) ;
   - `lireEtatClient(stock, clientId)` → liste `{ connecteur, etat, dernierOk, bandeau }` triée par nom de connecteur, lue sans recalcul.
2. Tests (faux `PortEssai` et faux `PortSante` en mémoire, connecteurs et clients fictifs comme `banque-fictive`, `client-a`) :
   - `d1-trois-jours-simules` : échec, échec (dégradé, bandeau `connecteur_degrade`), succès (ok, bandeau retiré) ;
   - `un-echec-reste-ok` ; `essai-qui-leve-compte-comme-echec` ; `delai-depasse-compte-comme-echec` (minuterie de vitest) ;
   - `relance-le-meme-jour-idempotente` ; `alerte-une-seule-fois-au-passage-en-degrade` ;
   - `un-client-n-en-voit-pas-un-autre` (échec chez `client-a` seulement, `client-b` reste ok ; jamais deux clients en cours en même temps) ;
   - `etat-lu-trie-par-nom` (liste vide acceptée, `dernierOk` nul accepté) ; `seuils-invalides-propages` (NaN, 0, non entier, panne <= dégradé : erreur de L14-T07 remontée).
3. Journal `pilotage/journal/L14-T38.md` (10 lignes au plus) ; `statut: fait`.
