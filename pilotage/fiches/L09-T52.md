## Contexte
Seconde moitié de l'ancienne L09-T49, découpée par L00-T84. Même cadre : décisions de Will du 09/11/2026 (D42, D29) et J3a du 07/11/2026 avec ses quatre conditions (données FICTIVES ; relecture Opus ; aucune production sans J10 ; console derrière une interface et un faux service).

Spec 09, §04 : `POST /profil/changements` exige la réauthentification pour forme, régime de TVA, impôt et dates ; §01 : `confirme_par` = personne en session, jamais un agent.

## À faire
1. Réauthentification par `exigerNouvelleConnexion` (L00-T50) pour les clés forme, regime_tva, regime_imposition, exercice_debut, exercice_fin, sur la confirmation d'un changement et d'un champ ; refus `REAUTHENTIFICATION_REQUISE` 401. Le noyau n'a pas d'opération propre au profil et n'en reçoit pas (`types.test.ts` en compte 8) : passer une opération sensible existante, comme `isolation-interface.ts`, avec un commentaire ; toutes exigent la même fraîcheur de connexion.
2. `confirmePar` tiré de la session (personne) ; une session qui n'est pas une personne est refusée (`CONFIRMATION_PAR_AGENT` 403). Services : paramètre final optionnel `confirmePar` ; la valeur actuelle reste par défaut pour le faux serveur et les tests existants du contrat, qui ne changent pas.
3. `app.ts` : réglages de connexion et horloge passés aux routes depuis `options` (lus à un seul endroit, valeurs d'exemple fictives) ; revendications lues sur la session vérifiée que L09-T49 met au contexte.
4. Tests nommés (`profil-reauthentification.test.ts`, faux `creerFauxSessions`) : `reauthentification-requise`, `reauthentification-acceptee`, `agent-ne-confirme-pas`, `confirme-par-personne-de-session`, `cles-non-sensibles-sans-reauthentification`.

## Hors périmètre
Préfixe et session exigée (L09-T49, déjà fait) ; noyau ; faux serveur ; écrans ; base (L09-T48).

## Pièges
Sensible (sécurité, droits) : double relecture. Ne retirer ni la session exigée ni le préfixe de société posés par L09-T49. Aucune adresse, aucun secret, aucun identifiant réel dans le code ni les tests.
