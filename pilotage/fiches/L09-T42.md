## Contexte
Spec 09, §04 règle 2 : « Chaque changement dit son effet avant d'être fait » : l'aperçu rend brouillons recalculés, déclarations non déposées, échéances déplacées, écritures validées touchées = 0 ; rien n'est enregistré sans « Confirmer ». Règle 3 : effet antérieur à une période déposée = refus. **Prérequis hors lot** : la fonction `ecrire()` d'`apps/web/src/api.ts` (fiche L07-T26 du lot 07) doit être sur main avant de tirer cette fiche ; ne JAMAIS ajouter une seconde fonction d'écriture.

## À faire
1. `Modification.tsx` : formulaire d'un champ (valeur, date d'effet) ; « Voir l'effet » appelle `POST /profil/changements/apercu` par `ecrire()` ; affichage de l'aperçu (nombres et périodes, phrase « Aucune écriture validée n'est modifiée ») ; « Confirmer » appelle `POST /profil/changements` avec `apercuId` ; refus `PERIODE_DEPOSEE` affiché par `phraseDeCode` ; `APERCU_PERIME` = nouvel aperçu demandé ; bouton désactivé pendant l'envoi (pas de double envoi).
2. `Ecran.tsx` : bouton « Modifier » par champ qui ouvre `Modification` (ajout seulement).
3. `e45.ts` : textes ajoutés.
4. Tests nommés (MSW, L09-T37) : `apercu-avant-confirmation`, `rien-sans-confirmer` (fermer après l'aperçu : `GET /profil` inchangé), `confirmation-met-a-jour-l-ecran`, `periode-deposee-message`, `apercu-perime-redemande`, `pas-de-double-envoi` (deux clics rapides : un seul appel), `date-d-effet-invalide-refusee-avant-envoi` (`2026-02-30`, vide), `focus-sur-le-message-d-erreur` (accessibilité).

## Hors périmètre
Pas de réauthentification (L09-T49, bloquée) ; ne pas modifier `api.ts`.

## Pièges
Comme L09-T41. Une clé d'idempotence par intention (aperçu, confirmation), pas une par clic.
