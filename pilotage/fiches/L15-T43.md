## Contexte
Spec 15, CA-R1 (`GET /calendrier?du=&au=`) et PR-R3 (`GET /vocabulaire?mode=` : `mode` change les mots, jamais la place des choses ni les données ; un terme n'est publié qu'après validation par 3 comptables, `validePar >= 3` ; avant, le terme simple est rendu sans survol). Décision de Will en attente sur E15 et E16 (point P3) : sans effet ici. Échéances « à vérifier » rendues avec leur `sourceUrl` (D31, D44).

## À faire
1. `domaines/calendrier.ts` : routes `lireCalendrier` (`GET /exercices/{exercice}/calendrier`, query stricte `du`, `au` AAAA-MM-JJ obligatoires ; `du` après `au` = 400 `ORDRE_INVERSE`) et `lireVocabulaire` (`GET /vocabulaire`, query `mode` parmi `simple`, `comptable`) ; réponses `{ body: LigneEcheance[] }` et `{ body: { code; mot; survol? }[] }`.
2. `domaines/calendrier-service.ts` : `calendrier` et `constatsDateIntrouvable` de L15-T19 sur les échéances fictives (L15-T30), société et exercice fictifs fixés ; vocabulaire : en mode `simple`, `mot = simple` et `survol = comptable` si `validePar >= 3` ; en mode `comptable`, `mot = comptable` si `validePar >= 3`, sinon `simple` ; `survol` absent si `validePar < 3`. La règle « 3 comptables » est une constante du service.
3. Domaine déjà branché par L15-T69 (objet vide) : remplir l'objet du domaine dans son fichier du contrat et la fonction de routes de son fichier serveur (implémentation par le service), SANS toucher `routes.ts` ni `app.ts` ; régénérer `openapi.json` (`pnpm contrat:openapi`).
4. Tests nommés : `calendrier-trie-inconnues-a-la-fin`, `a-verifier-avec-source`, `date-absente-inconnue`, `ordre-inverse-400`, `date-invalide-400` (`2026-02-30`), `exercice-inconnu-404`, `vocabulaire-simple-avec-survol`, `terme-non-valide-sans-survol`, `mode-comptable-memes-codes` (mêmes codes, dans le même ordre, dans les deux modes).
