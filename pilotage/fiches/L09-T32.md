## Contexte
Spec 09, §04 : `GET /parametres?cle=…&date=…` (valeur, statut, source, date de relevé). §03 règle 2 : pas de ligne pour la date = IMPOSSIBLE, jamais de valeur par défaut ; règle 3 : statut ≠ `valide` = l'écran affiche « à vérifier », la source et la date. Cas P20.

## À faire
1. `packages/contrat/src/domaines/parametres.ts` : schéma `ParametreLu { cle; valeur; statut; effetDebut; effetFin: string | null; source: { url; titre; maj: string | null }; dateReleve; aVerifier: boolean }`, `ReponseParametre` ; route `lireParametre` (`GET /parametres`, query `cle` (1 à 100 caractères, `[a-z0-9_.]`) et `date` stricte, toutes deux obligatoires) ; erreur `PARAMETRE_ABSENT` 404 (données : `cle`, `date`).
2. `parametres-service.ts` : lecture sur les paramètres INVENTÉS de `genererProfils()` (L09-T29) ; fin EXCLUE (même règle que `parametreAuJour`, L01-T14) ; `retire` ignoré ; `aVerifier = statut !== 'valide'`.
3. `routes.ts` : ajouter `parametres: { lireParametre }` ; régénérer `openapi.json`.
4. `apps/serveur/src/domaines/parametres.ts` + `app.ts`.
5. Tests nommés : `parametre-en-vigueur`, `absent-404-jamais-de-defaut`, `fin-exclue`, `retire-ignore`, `a-verifier-si-non-valide-p20`, `query-invalide-400` (clé vide, clé avec espace, date `2026-13-01`, date absente), `serveur-repond-au-parametre`.

## Hors périmètre
Pas de lecture du vrai catalogue (`packages/parametres/src/catalogue/`) par le serveur en mémoire : le contrat n'importe pas `packages/parametres` ici ; branchement réel avec la base (L09-T48, bloquée).

## Pièges
Comme L09-T30. Une erreur 404 ne doit jamais porter une valeur de repli dans son corps.
