## Contexte
bloque_par: V1 : ne pas planifier avant la fin de la V0 (décision de Will, 11/11/2026)
Modèle `mandat` : mandant, mandataire (personne ou outil), portée (liste d'actions de `securite/types.ts`), début, fin, `revoque_le`. Le mandat est relu à CHAQUE requête, sans cache : une révocation vaut dès la requête suivante. Un mandat auprès de l'administration reste hors du produit : on enregistre seulement sa preuve (empreinte d'un document), on ne l'exerce jamais. Modèle voisin : `securite/expert.ts` (accès de l'expert invité) ; garde de route voisine : `apps/serveur/src/garde-acces.ts`.

## À faire
1. Tests d'abord, mandats fictifs (identifiants inventés).
2. Noyau `mandats.ts` (pur) : `verifierMandat(mandat, demande, maintenant)` → `{ permis: true } | { permis: false; raison: 'mandat_revoque' | 'mandat_expire' | 'mandat_pas_commence' | 'hors_portee' }` ; `revoquer(mandat, par, horodatage)` (nouvel objet, l'ancien figé) ; `preuveMandatAdministration(empreinte)` ne crée aucune portée d'action.
3. Serveur `garde-mandat.ts` : `creerGardeMandat({ lireMandat, journaliser, horloge })` ; `lireMandat` est appelé à chaque requête (aucune mémoire entre deux appels) ; refus = 403 et une ligne de journal `mandat.refuse` (identifiants seulement, aucune donnée de pièce).
4. Tests nommés : `mandat-valide-permis`, `hors-portee-refuse`, `mandat-expire-refuse`, `revocation-puis-appel-403`, `une-ligne-journal-par-refus`, `lecture-a-chaque-requete-sans-cache`.
