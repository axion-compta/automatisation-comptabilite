## Contexte
bloque_par: V1 : ne pas planifier avant la fin de la V0 (décision de Will, 11/11/2026) ; menu à confirmer par Will (décision fondateur de V3-UX-097) ; correspondance avec les rôles du portail V3-ROL-002 (autre domaine V1).
Le menu est une seule source (`apps/web/src/socle/menu.ts`, L01-T33). Les capacités viennent du serveur (`apps/web/src/socle/capacites.ts`, refus par défaut). Raccourcis d'une lettre : `apps/web/src/commandes/lettres.ts` (L15-T58). Le rail replié de 72 px existe déjà (`menu_etat = reduit`). Le vrai refus reste au serveur ; le front ne fait qu'éviter d'afficher.

## À faire
1. Tests d'abord.
2. `menu.ts` : chaque entrée déclare l'action de capacité qui l'ouvre ; `menuPour(capacite)` ne garde que les entrées permises ; capacité inconnue ou en chargement = entrée cachée. Les profils dirigeant, gestionnaire, expert et lecteur se testent par des capacités fictives, jamais par un rôle deviné côté client.
3. `routeur.tsx` + `EcranInterdit.tsx` : une URL d'écran dont l'entrée est refusée affiche le code 403, une phrase et un lien vers `/` ; aucun contenu de l'écran n'est monté.
4. `sequence-g.ts` : `g` puis une lettre dans un délai d'interface (constante nommée) = aller au chemin associé ; ignoré dans un champ de saisie ou une fenêtre modale ; coupé si `raccourcis.actifs = false`.
5. Tests nommés : `dirigeant-voit-tout-son-menu`, `lecteur-sans-reglages`, `capacite-inconnue-entree-cachee`, `url-interdite-affiche-403-et-lien-accueil`, `g-puis-lettre-navigue`, `g-dans-un-champ-ignore`, `g-expire`.
