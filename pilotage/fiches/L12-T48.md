## Contexte
Débloquée par la décision de Will du 07/11/2026 : D29 et J3a donné avec quatre conditions (données FICTIVES seulement ; fiche sensible relue par Opus ; aucune production sans le feu vert J10 ; ce qui exige le vrai schéma de la console s'écrit contre une INTERFACE et un faux serveur). Le schéma réel `a_compta` (module C4 de la console, ADR 0060) n'est pas livré : AUCUNE base réelle, aucune migration exécutée, aucun test sur base.
Fiche corrigée le 08/11/2026 : la version précédente exigeait une migration réelle et des tests sur base de test, ce que J3a interdit ; un auteur l'a donc bloquée.
Spec 12, `01-socle-catalogue` §Journal (V3-CTL-070) : table `journal_verification` en ajout seul (id, horodatage, déclencheur, règle, version de la règle, objet, résultat, valeur, écart, version des paramètres) ; un déclencheur refuse UPDATE et DELETE ; colonnes ajoutées à `regle_controle` (exigence, regle_code, bloque, declencheurs, phase, test_id, parametres, actif). Cas CT-40 (pièce contrôlée à l'arrivée, la nuit et avant export : toutes les lignes présentes, réussites comprises ; modification refusée).
Briques : `LigneJournal`, `ErreurJournal`, `ajouterAuJournal`, `historiqueObjet` de L12-T24 (`packages/noyau/src/controles/journal.ts`), importés par chemin relatif comme `apps/serveur/src/persistance/declarations.ts`.

## À faire
1. Tests d'abord, données fictives, horloge fixe, identifiants injectés.
2. `journal-verification.ts` (types et interface, sans état) : `interface JournalVerification { ajouterLot(ctx, lignes); historique(ctx, objet); modifier(ctx, id, changements); supprimer(ctx, id) }` (toutes `Promise`) ; `CodeJournalVerification = 'ajout_seul' | 'inconnu' | 'contexte_invalide' | 'ligne_invalide'` et `class ErreurJournalVerification` (champ `code`, message = code seul, jamais une valeur). La société vient TOUJOURS du contexte.
3. `journal-verification-memoire.ts` : `creerJournalVerificationMemoire(options: { nouvelId: () => string })` qui porte les règles de la table : `ajouterLot` ajoute toutes les lignes ou aucune ; `historique` rend les lignes d'un objet de la société du contexte, par horodatage puis ordre d'ajout ; `modifier` et `supprimer` lèvent TOUJOURS `ajout_seul` (même pour un id inconnu) et ne changent rien ; les lignes rendues sont des copies (modifier une copie ne change pas le journal).
4. `journal-verification-memoire.test.ts`, tests nommés : `CT-40`, `modification-refusee`, `suppression-refusee`, `lot-tout-ou-rien`, `historique-ordonne`, `isolation-societe`, `copie-non-modifiable`, `reussites-ecrites`.
5. `sql/a_compta-journal-verification.sql` écrit comme TEXTE, jamais exécuté, hors du dossier `apps/serveur/src/base/migrations` : `CREATE TABLE IF NOT EXISTS a_compta.journal_verification` (colonnes ci-dessus), index sur (objet, horodatage), fonction et déclencheur `BEFORE UPDATE OR DELETE` qui lèvent une exception, `ALTER TABLE a_compta.regle_controle ADD COLUMN IF NOT EXISTS` pour chacune des 8 colonnes. Ajout seul : aucun DROP, aucun RENAME. Le numéro réel de migration sera pris quand le schéma de la console sera livré.
6. `journal-verification-sql.test.ts` : lit le fichier (`readFileSync`) et vérifie la présence de la table et de ses 10 colonnes, de l'index, du déclencheur sur UPDATE et DELETE, des 8 colonnes de `regle_controle`, de `IF NOT EXISTS` sur chaque création ou ajout (rejouable), et l'absence de DROP et de RENAME.
7. Journal `pilotage/journal/L12-T48.md` (10 lignes au plus, cite « débloquée par D29 et J3a du 07/11/2026 »), statut `fait`.
