## Contexte
Suite de L07-T14, même méthode (contrat figé, domaines branchés sur des bouchons 501). Spec 07, `03-fin-contrat-gel.md` : accusé de réception (`POST …/fin-contrat/accuse`, `Idempotency-Key`), gel avec motif obligatoire ; `04-plans-cgv-mise-en-service.md` §2 : documents contractuels et acceptations. Écart volontaire à la spec : la levée du gel est `POST /fin-contrat/gel/levee` (et non `DELETE …/gel`), parce qu'un `DELETE` avec un corps (le motif est obligatoire) est mal transmis par certains intermédiaires ; à noter au journal.

## À faire
1. `packages/contrat/src/domaines/fin-contrat.ts` : schéma `EtatFinContrat = { statut: 'aucune' | 'preavis' | 'remis' | 'accuse'; date_fin: date | null; remis_le: horodatage | null; manifeste_empreinte: 64 hexa | null; accuse_le: horodatage | null; efface_prevu_le: date | null; gel: { actif: booléen; motif: chaîne | null; pose_le: horodatage | null }; gel_console: booléen }` ; routes (toutes `tags: ['acces:compte']`, en-tête `EnTeteEcriture` sur les POST) : `lireFinContrat` (`GET /fin-contrat`), `accuserReception` (`POST /fin-contrat/accuse`, corps `{ manifeste_empreinte }`, erreurs `PAS_DE_REMISE` 409, `DEJA_ACCUSE` 409, `EMPREINTE_DIFFERENTE` 422), `poserGel` (`POST /fin-contrat/gel`, corps `{ motif }` : chaîne `trim()` de 1 à 500 caractères, erreur `GEL_DEJA_ACTIF` 409), `leverGel` (`POST /fin-contrat/gel/levee`, corps `{ motif }`, erreur `GEL_INACTIF` 409) ; toutes rendent `EtatFinContrat`.
2. `acceptations.ts` : `listerDocumentsAAccepter` (`GET /documents-contractuels/a-accepter`, `tags: ['acces:compte']`) → `{ body: { type; version; approuve_le; empreinte; sources: chaîne[] }[] }` ; `enregistrerAcceptation` (`POST /acceptations`, `operationId: 'enregistrerAcceptation'`, `successStatus: 201`, en-tête Idempotency-Key, corps `{ type; version: entier >= 1 }`, `tags: ['acces:compte']`) → `{ type; version; accepte_le }` ; erreurs `VERSION_PERIMEE` 409, `DOCUMENT_ABSENT` 404.
3. `routes.ts` : ajouter `finContrat: { lireFinContrat, accuserReception, poserGel, leverGel }` et `acceptations: { listerDocumentsAAccepter, enregistrerAcceptation }` ; régénérer `openapi.json`.
4. `apps/serveur/src/domaines/fin-contrat.ts` et `acceptations.ts` : `implementerFinContrat(os, options: OptionsAbonnement)` et `implementerAcceptations(os, options)` (bouchons 501, même forme que L07-T14) ; branchés dans `app.ts`.
5. Tests nommés : `fin-contrat-et-acceptations-dans-openapi`, `post-avec-idempotency-key` (`routesEcritureSansEnTete()` reste `[]`), `motif-vide-ou-blanc-refuse-par-le-schema` (`''`, `'   '`, 501 caractères), `etiquette-acces-compte-partout`, `six-routes-branchees` (statut différent de 404, sans exiger 501), `version-non-entiere-refusee-400` (0, -1, 1.5, `"2"`).

## Hors périmètre
Aucune logique (L07-T20, L07-T21), pas de faux serveur (L07-T16), pas de permission ni de réauthentification (fiche bloquée L07-T37).

## Pièges
Même limite de 400 lignes que L07-T14 ; si elle est dépassée, retirer `acceptations.ts` et le signaler (une fiche de plus sera créée). Les noms `implementerFinContrat`, `implementerAcceptations` sont un contrat entre fiches. La longueur maximale du motif (500) est une limite technique du schéma, pas une valeur légale : la commenter comme telle. Le motif peut contenir des données personnelles : ne jamais le journaliser dans un log technique. Aucun operationId ne commence par un préfixe de VERBES_SENSIBLES sans entrée dans ROUTES_A_GESTE (gestes-routes.test.ts).
